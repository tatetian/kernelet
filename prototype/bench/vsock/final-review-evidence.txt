Comparison fairness

The guest caller, request sizes, timed/warmup counts, full-transfer loops,
sequence word, complete reply verification and directional 64 KiB capacities
are common. Virtio endpoints set 64-bit AF_VSOCK buffer options and read back
the resulting size on both connecting and accepted sockets. Credits do not
bound every skb/virtqueue allocation; the page correctly says so. The workload
is one outstanding echo, with both directions counted in goodput; it is not a
one-way saturation benchmark. Per-case p50/p95 medians are labeled accurately.

This is actual modern virtio PCI/MSI-X with vhost-vsock in one KVM VM, without
nesting. Every retained data-queue IRQ has effective guest CPU1 affinity, an
unchanged CPU0 count and increasing CPU1 count. Config-vector effective CPU0
does not contradict the narrower data-queue placement claim. No callback or
workqueue placement is inferred from interrupt delivery.

Recorded vCPU/vhost affinities match physical CPUs 0/1, with housekeeping on 2.
The runner selects different package/core IDs rather than SMT siblings; current
sysfs corroborates cores 0/1/2 with sibling lists 0,4; 1,5; 2,6. Native outer
Linux 6.8 peer versus guest Linux 6.12 pipe/klet peer remains a material topology
and kernel difference. The page states it prominently and does not disguise
this as an identical native deployment or a measured copy-count audit of 6.8.
Neither powersave governor, unmanaged sibling activity, nor unrelated host
load is silently treated as controlled. These prevent generalizing small
differences, especially the roughly 1% klet/pipe difference at 16 KiB.

CPU scope and boundaries

Endpoint CPU includes caller and peer, with asynchronous vhost work absent
from virtio's endpoint sum. QEMU task runtime explicitly excludes the identified
vhost TID before adding its runtime separately. This worker belongs to QEMU's
task list in the retained metadata. The outer sum includes guest execution and
the outer peer, so adding endpoint and outer CPU would double count. The page
correctly forbids that addition and disclaims all-machine CPU accounting.

The unchanged 200000 ns KVM halt-poll maximum is recorded. Pipe/klet outer CPU
is strongly affected by configured vCPU polling; the page calls this monitored
configured-system cost and does not infer transport CPU from it. No idle
subtraction or artificial host-global tuning is concealed.

Outer windows include begin acknowledgement and end token, and task snapshots
are sequential. For mode 2, median outer-wall excess is about 0.49-0.65% for
klet and 0.009-0.026% for virtio across sizes; maximum klet excess is 1.48%.
These are small relative to the large virtio separation, but preclude treating
very small outer CPU differences as precise marginal transport cost. The raw
intervals are retained and the page discloses the boundary cost. Virtio uses
its data stream for control; the other paths use a separate control stream.

Profiling and optimization attribution

Raw 64 KiB tenant profile records agree with every diagnostic table entry.
Both modes perform 4160 read and 4160 write copies of 272629760 bytes each;
host copies total 545259520 bytes. The comparison is not based on instrumented
goodput. Mode 0 issues 33280 data blocking notifications versus 8319 in mode 2;
mode 2 additionally issues 16640 poll notifications. Wait/retry observations
fall from 28928/20608 to 8321/1. These count instrumented events, not recipients,
hardware interrupts, or exact sleeps inside the queue.

Read commit elapsed time changes from 41.319946 to 1.433550 ms, while write
commit changes from 41.251675 to 44.269658 ms. The page correctly avoids adding
overlapping intervals or attributing whole elapsed spans to wakeup CPU work.
Similar copy and lookup intervals, fewer unsuccessful retries, source mechanism
and uninstrumented ablation jointly support the notification optimization.
They do not isolate each scheduling cost. Mode 2 versus 1 is explicitly the
split-queue/demand-gating package. The direct API comparison changes both tenant
entry and memory access and retains the common host caller; its small advantage
does not isolate syscall cost. The page handles all of these limits correctly.

The retained plan and three pre-implementation reports explicitly review the
unoptimized broker fingerprint, give conditional permission to implement, and
require later correctness and matched benefit before selecting a default.
The implementation review identifies the later broker fingerprint and checks
the conditions. This is a credible recorded review workflow; the final evidence
does not treat design approval itself as a performance or correctness proof.
The deliberate manual module default 0 versus experimental Make default 2 is
explicit and poses no inconsistency.
